01 CONTEXT

不是嵌入一个页面，而是接入一套交易能力

用户只看见一次扫码，背后却横跨三套系统。项目的核心，是让入口、资金与充电履约在同一条体验里成立。

和包提供用户入口、身份与支付能力；特来电提供电站、充电枪、启停控制和最终账单；觉观承接 H5、用户映射、权益、订单、支付编排、退款补缴与状态同步。产品方案需要把三方清晰分工，同时保证用户始终感受到这是和包内的一次连续充电服务。

01 / ENTRY

和包 / 中移金科

提供 App 入口、原生扫码、一次性 Ticket、会员销售与和包支付能力。

边界：不直接创建充电订单，也不控制充电枪。
02 / ORCHESTRATOR

觉观

承载充电 H5 与交易中台，统一编排身份、权益、订单、支付、启停、结算和异常恢复。

价值：把分散能力转换为一条可执行、可恢复的业务流程。
03 / FULFILLMENT

特来电

提供电站与枪口状态、物理启停、实时充电数据和最终账单。

边界：不处理和包会员、支付和页面逻辑。

02 PRODUCT MODEL

先拆开三条链路，再让它们在结算处汇合

身份、权益、交易彼此关联，但不能互相替代。拆开权威来源，才能避免一个状态变化拖垮整条链路。

A / IDENTITY

无感身份链路

用户已登录和包，无需再次输入手机号。一次性 Ticket 只用于换取稳定用户身份，后续业务改用觉观自己的登录会话。

和包原生扫码 一次性 Ticket JINKE + userNo 觉观 JWT
B / BENEFIT

会员权益链路

和包会员商品映射觉观权益产品。购买成功后整包原子下发折扣卡与抵扣券，避免出现“部分到账、页面却显示开通成功”。

会员购买 权益包映射 原子下发 结算核销
C / TRANSACTION

充电交易链路

围绕和包支付与特来电履约建立订单状态机，覆盖预付、自动启充、实时充电、最终账单、退款或补缴。

扫码预检 预付款 充电履约 资金闭环
03 CORE JOURNEY

从扫码到订单完成

主流程不把“支付成功”直接等同于“充电成功”。每个阶段都有独立事实来源、页面状态和允许操作，用户返回页面时也能从当前权威状态继续。

01

扫码登录

和包完成原生扫码，携带二维码原文与一次性 Ticket 进入觉观 H5。

02

业务预检

校验站枪状态、进行中订单、启动失败订单与未支付超时费。

03

预付款

创建订单与和包收银台；页面回跳后重新查询，不能把回跳当成支付成功。

04

自动启充

付款确认后服务端自动启动，依次展示准备启动、正在启动和充电中。

05

充电监控

H5 展示费用、电量、SOC、功率与时长；停止操作需二次确认。

06

最终结算

物理结束后等待最终账单，再结合用户权益计算实际消费。

07

资金闭环

余额原路退款，不足创建补缴；资金处理完成后订单才进入完成态。

PAYMENT · PAID 钱已到账

不代表充电已开始。

ORDER · CHARGING 物理充电已开始

只有此时才能展示“充电中”。

ORDER_SETTLED 最终金额已算清

仍可能等待退款或补缴。

ORDER · COMPLETED 整笔订单已闭环

账单、权益和资金均已处理。

04 STATE & RECOVERY

关键设计不在顺利流程，而在结果不确定时

跨系统链路一定会遇到延迟、乱序和未知结果。产品规则必须先回答：此刻用户能做什么，系统绝不能做什么。

PAYMENT_UNKNOWN

支付结果确认中

继续查询原支付单，页面提示“请勿重复支付”；不能因为回跳或超时直接创建另一笔付款。

START_FAILED_WAIT_ACTION

启动明确失败

默认 30 分钟内允许重试原枪、换枪或取消；用户无操作后自动取消并发起全额退款。

START_UNKNOWN

启动结果未知

只查询原启动流水，暂不展示重试、换枪或退款入口，防止一笔预付款启动两把枪。

REFUND / SUPPLEMENT

结算后资金未闭环

差额退款与全额退款共用原订单；消费超出预付时明确展示“待补缴”，不笼统写成待付款。

场景 用户看到 允许操作 系统约束
收银台未支付 待支付金额、剩余时间、失效说明 继续支付 / 取消订单 超时后关闭原支付单，不长期停留在待付款
预付后未启动 等待启动倒计时与退款规则 按状态重试、换枪或取消 超时或用户取消后，全额原路退款
充电后有余额 实际消费、退款金额与退款路径 查看退款进度 / 联系客服 退款成功后，订单才进入已完成
最终消费超出预付 待补缴金额与形成原因 完成补缴 不混淆为首次预付款未成功
05 PRODUCT DECISIONS

缩短主链路，守住业务边界

技术方案给出系统能力，产品决策决定它如何进入用户流程。每一项取舍都要同时回答：体验是否更短，边界是否更清楚。

我将影响主链路的关键分歧整理成明确规则，使页面、研发与测试面对同一个业务结果时，能够做出一致判断。

01 PREPAY → START

支付确认后自动启充

不让用户为同一件事确认两次。

预付款到账后由服务端自动发起启动，用户无需再次点击“开始充电”；页面仍严格区分预付款成功、准备启动、正在启动和充电中。

边界 PAYMENT PAID 只代表钱已到账，只有订单进入 CHARGING 才表示物理充电开始。
02 ORDER RECOVERY

优先恢复原订单

再次扫码不是重新建单的理由。

用户返回或再次扫码时，先判断是否存在进行中、启动失败或结果未知的订单，再按状态提供继续查看、重试、换枪或取消。

结果 减少重复订单和重复付款；启动结果未知时锁定高风险操作，只查询原启动流水。
03 REFUND MODEL

退款留在原充电订单

退款是资金过程，不是另一笔用户订单。

充电后的差额退款与未启动的全额退款都写回原订单详情；通过退款原因、金额与状态区分业务结果，不再生成一条独立的用户可见订单。

结果 用户能在同一处同时看到预付、实际消费与退款去向，避免把差额退款误解为整单退款。
04 OVERTIME FEE

超时占用费独立成单

充电消费与占用责任分开表达。

超时占用费不并入原充电订单的实际消费，使用独立订单记录计费、减免与支付状态；存在未支付超时费时，可限制创建新的充电订单。

结果 用户明确知道为什么需要再次付款，账单与对账也不会混淆充电费用和占用费用。
05 FINAL BILL → SETTLEMENT

最终账单才是结算起点

实时费用负责感知，最终账单负责交易。

物理充电结束后先进入账单生成中，待特来电最终账单到达再计算权益优惠、实际消费、应退或应补金额。用户可主动确认；长时间未操作时，再由系统按约定规则完成结算。

边界 实时累计费用不能替代最终账单；ORDER_SETTLED 表示金额已算清，退款或补缴完成后订单才进入 COMPLETED。
06 CONSISTENCY

事件负责及时，查询负责权威

多方系统不追求“永不延迟”，而是建立一套不重复、不倒退、可补偿的恢复机制。

Event

通知刚刚发生了什么

订单、支付、结算、退款和超时费通过统一事件同步，帮助和包及时更新订单镜像。

Query

查询现在到底是什么

页面打开、通知丢失或结果有疑问时，主动查询订单、支付或退款详情，以当前结果为准。

Recovery

用唯一标识处理重复和乱序

同一事件只处理一次，资源版本只向前更新；未知结果始终查询原流水，不另起一笔交易。

07 DELIVERY

把技术契约翻译成可执行的产品规则

本阶段的交付重点不是包装结果数字，而是将多方接口约束转化为研发、设计和测试能够共同使用的业务语言。

01

全链路流程

覆盖扫码、预付、自动启充、充电、结算、退款补缴与订单恢复。

02

状态与动作矩阵

明确每个订单、支付和退款状态的页面文案、用户动作与系统禁区。

03

页面字段规范

统一待支付、充电中、支付成功、账单详情与退款页的金额和时间层级。

04

对接与联调清单

沉淀三方职责、接口调用时机、异常恢复与待确认项，支撑后续联调。

项目状态说明

当前材料为方案设计与联调前对齐版本，正式域名、部分接口开放时间及个别协议细节仍以双方联调结论为准。页面不使用未经验证的覆盖人数、转化率或业务增长指标。
